# ADR-0026 — Durable Agent Audit Model

**Status:** Accepted · **Milestone:** M9 · **Date:** 2026-08-22

## Context
Memory (M7, Redis) helps the agent reason and expires; guardrail/confirmation state (M8, Redis) is
short-lived. Neither is a durable record of what the system actually did. We need a permanent,
queryable execution history, written from backend-observed facts (never reconstructed from prompts,
never written by the LLM, never sourced from logs).

## Decision
- **Three typed tables**, not a generic `audit_events` table: `agent_executions` (one per run),
  `agent_steps` (ordered transitions), `tool_executions` (real tool calls). Guardrail and confirmation
  outcomes are typed `agent_steps` (`step_type` + `detail_code`), keeping the model self-describing.
- **House conventions:** `BIGINT GENERATED BY DEFAULT AS IDENTITY` surrogate PK plus a **UUID natural
  key** per table (`execution_uid`, `tool_execution_uid`) for idempotency; `TIMESTAMPTZ`→`Instant`;
  `owner_id`→`users(id) ON DELETE CASCADE`; enums as `VARCHAR` + mirroring `CHECK`; Flyway **V5**;
  portable SQL (PostgreSQL + H2 PG-mode); indexes tied to real query patterns.
- **Plain FK id columns** (no JPA associations) — the read model queries steps/tools by `execution_id`,
  matching the M3 `owner_id` convention and avoiding lazy-loading.
- **No Hibernate Envers, no generic row-audit framework, no new dependency.**

## Alternatives considered
- A single generic `audit_events` table (rejected: loses typed semantics; the brief and query patterns
  favor explicit tables).
- Hibernate Envers (rejected: generic row versioning, not agent-execution semantics).

## Consequences
- Clear, queryable, owner-scoped history; idempotent writes under retry.
- Verified by `AgentAuditPersistenceIT` (round-trip, constraints, filtering) and `AgentAuditE2EIT`.
