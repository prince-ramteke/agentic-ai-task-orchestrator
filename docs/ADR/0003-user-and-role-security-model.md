# ADR-0003: User and Role security model

- **Status:** Accepted
- **Date:** 2026-08-21
- **Deciders:** Prince Ramteke
- **Milestone:** M2 — Authentication & Authorization

## Context
M2 introduces the first persisted domain: accounts and their roles. The model must support `USER` and `ADMIN` today and remain extensible to more roles without redesign, per `docs/DATABASE.md`.

## Decision
- **Roles as an entity** (`roles`) with a **many-to-many** mapping to `users` via a `user_roles` join table — matching the conceptual model in `docs/DATABASE.md`. New roles are added as rows, not code/schema changes.
- **Role name = Spring Security authority** (`ROLE_USER`, `ROLE_ADMIN`). `hasRole('ADMIN')` maps to authority `ROLE_ADMIN`; the JWT `roles` claim and `SimpleGrantedAuthority` use the same strings — one representation end to end.
- **Primary keys:** `BIGINT GENERATED BY DEFAULT AS IDENTITY` (JPA `IDENTITY`). Internal ids are never exposed by public auth responses, so sequential ids pose no enumeration risk here. (Supersedes the "PK type chosen at M3" note in `docs/DATABASE.md` for the security tables.)
- **Email is the identity**, stored **normalized** (trimmed, lower-cased) so the `UNIQUE(email)` constraint is genuinely case-insensitive. Normalization happens in the service before persistence and lookup.
- **Roles are eagerly fetched** on `User` (few rows; needed to build authorities at login; `open-in-view=false`).

## Alternatives considered
- **Enum-backed roles (no table):** simpler, but the docs commit to a role entity and a join table for extensibility; an enum makes adding roles a code+deploy change.
- **UUID primary keys:** useful when ids are exposed externally; unnecessary complexity here since ids aren't surfaced. Revisit if a public resource ever exposes its id.
- **Storing role names without the `ROLE_` prefix:** would require prefix juggling between DB, token, and Spring authorities; storing the authority verbatim is simplest and least error-prone.

## Consequences
- Adding a role later = one seed row + granting it server-side; no schema redesign.
- The client can never choose a role: `RegisterRequest` has no role field, and public registration always grants `ROLE_USER` (see ADR-0004 and `docs/SECURITY.md`).
- Admin creation is a controlled, server-side operation (no self-service escalation).
