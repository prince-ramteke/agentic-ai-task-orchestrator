# M9 — Durable Agent Audit & Execution History (Design Spec)

- **Status:** APPROVED (design) — implementation not started
- **Date:** 2026-08-22
- **Author:** prince-ramteke (with Claude)
- **Milestone:** M9 (builds on M2 auth, M3 Postgres/Flyway, M6 orchestration, M7 memory, M8 guardrails)
- **Boundary:** M10 owns broader observability/dashboards. M9 persists **what actually happened**.

> **Memory helps the agent reason. Audit records what the system actually did.** Audit is durable,
> queryable PostgreSQL data written from **backend-observed execution facts** — never reconstructed
> from prompts, never sourced from logs, never written by the LLM, and never on the decision path.

## 1. Objective & non-goals

Introduce a durable, owner-scoped, queryable history of agent executions: one `agent_executions` row
per run, ordered `agent_steps`, and `tool_executions` for real tool calls, plus a read API.

**Non-goals (scope guard):** no new planning logic, no new tools (a test-only tool only if strictly
needed), no Redis/guardrail redesign, no Kafka/streaming, no Elasticsearch/OpenSearch, no analytics
warehouse/data lake, no distributed tracing, no Prometheus/Grafana dashboards (M10), no semantic
search, no Hibernate Envers, no generic row-audit framework, no automatic deletion scheduler.

## 2. Locked decisions (from approval)

1. **Failure policy — best-effort.** Each audit write is its own short transaction (never spanning an
   LLM/tool call). A failed write never blocks or rolls back the agent run; it is surfaced as a WARN
   log + `audit.write.failure` metric. Audit is authoritative **when present** because it is written
   from backend-observed facts. We do **not** claim guaranteed capture: a tool side-effect can commit
   while its audit row fails — that gap is recorded, not hidden.
2. **Integration seam — listener/sink.** A minimal `AgentExecutionListener` interface in the agent
   package (no-op default bean) is called by the orchestrator/confirm service at lifecycle points; the
   audit module implements it and persists. The orchestrator stays repository-free and decoupled
   (boundary test still passes); audit is fully optional.
3. **Admin scope — user-owned only.** Read endpoints are scoped to the authenticated owner (non-owner →
   masked 404) for USER and ADMIN alike. No cross-user data path ships in M9; an explicit RBAC-gated
   admin audit endpoint is a documented later decision.
4. **Payload — metadata + hashes + bounded final summary.** No raw prompt, no raw tool arguments, no
   raw LLM output, **no chain-of-thought**. Store safe metadata, an `arguments_hash` (SHA-256, reusing
   M8 canonicalization), and a length-capped `final_response_summary` (config default ~500 chars).

## 3. Data model (Flyway V5; three tables, no generic events table)

House conventions (M3): `BIGINT GENERATED BY DEFAULT AS IDENTITY` surrogate PK, `TIMESTAMPTZ`→`Instant`,
`owner_id`→`users(id) ON DELETE CASCADE`, enums as `VARCHAR` + mirroring `CHECK`, portable SQL
(PostgreSQL + H2 PG-mode). A **business UUID** natural key on each table gives idempotency.

## 4. Correlation ids
`execution_uid` (run) ⊃ `agent_steps.sequence` (ordered step) ⊃ `tool_execution_uid` (a TOOL_CALL
step's real execution). `conversation_id`/`request_id` tie back to M7 memory and to logs/metrics.
One family of ids, clearly nested — no parallel correlation systems.

## 5. Execution status (durable)
`STARTED` (created at run start) → terminal one of `COMPLETED`, `FAILED`, `TIMED_OUT`, `CANCELLED`,
`LIMIT_REACHED`, `LOOP_DETECTED`, `BLOCKED`, `PENDING_CONFIRMATION`. Maps 1:1 from `AgentStatus`
(M6/M8). `PENDING_CONFIRMATION` is a **real terminal state of the agent loop** (M8 does not auto-resume).
On a successful **confirm** of that run's action, the execution is promoted `PENDING_CONFIRMATION →
COMPLETED` (or `FAILED` if the confirmed tool failed) with `completed_at`/`duration_ms` refreshed and a
`CONFIRMATION_APPROVED` step + `tool_execution` appended. `RUNNING` is **not** persisted as a distinct
state (short runs; `STARTED` until terminal) — avoids an extra write per run.

## 6. Step types (stable enum)
`LLM_DECISION`, `GUARDRAIL`, `TOOL_CALL`, `CONFIRMATION_REQUIRED`, `CONFIRMATION_APPROVED`,
`CONFIRMATION_REJECTED`, `FINAL`, `FAILURE`. No others without justification. Guardrail and confirmation
outcomes live in typed steps (`detail_code` holds the reasonCode) — **not** a generic events table.

## 7. Tool outcomes (distinct, never conflated)
`SUCCESS`, `FAILED` (tool ran and errored), `DENIED` (guardrail policy denial — no execution),
`NOT_EXECUTED` (unknown tool / never reached), `CONFIRMATION_REQUIRED` (halted awaiting confirm),
`TIMEOUT` (pre-execution budget/deadline). Policy denial, tool failure, not-executed, and
confirmation-required are separate outcomes.

## 8. Lifecycle & listener seam
`AgentExecutionListener` (agent package; no-op default `NoOpAgentExecutionListener`):
- `onExecutionStarted(AuditExecutionStart)` — uid, ownerId, conversationId, requestId, startedAt.
- `onStep(AuditStep)` — executionUid, sequence, stepType, status, toolName?, detailCode?, timings.
- `onToolExecution(AuditToolExecution)` — toolExecutionUid, executionUid, stepSequence, toolName,
  riskLevel, outcome, errorCode?, argumentsHash?, confirmationId?, resultSummary?, timings.
- `onExecutionCompleted(AuditExecutionEnd)` — executionUid, status, finalResponseSummary?, iterations,
  toolCalls, completedAt, durationMs, failureCode?.

The orchestrator emits these at its existing lifecycle points (start of run; after each planner
decision; after each guardrail decision; around each tool execution; at terminate). Per-step timings
come from `System.nanoTime()` bracketing already present around each call — a **focused** change, not a
rewrite. The **confirm** path (`AgentConfirmationService`) emits `onStep(CONFIRMATION_APPROVED)` +
`onToolExecution(...)` + `onExecutionCompleted(...)` against the originating `executionUid` (a small
additive field threaded into the M8 confirmation record); cancel/expiry emits
`onStep(CONFIRMATION_REJECTED)` and leaves the execution terminal state unchanged (the side-effect never
happened — honest).

The event records are plain immutable carriers in the agent package; the audit module maps them to JPA
entities. The agent package gains **no** JPA dependency (boundary preserved).

## 9. Transaction & failure semantics
`AuditService` (audit module) implements the listener. Each method runs in its **own** short
transaction (`@Transactional(propagation = REQUIRES_NEW)`); no audit transaction ever spans an LLM/tool
call. All writes are **best-effort**: `AuditService` catches persistence exceptions, logs WARN, and
increments `audit.write.failure` — it never rethrows into the agent path. Ordering: `onExecutionStarted`
inserts the `STARTED` row; steps/tool rows insert as they occur; `onExecutionCompleted` updates the row
to terminal. If `onExecutionStarted`'s write failed, later step writes that reference a missing
execution are dropped (best-effort) and counted — never fatal.

## 10. Idempotency
Natural keys make writes safe under any double-invocation: `UNIQUE(execution_uid)`,
`UNIQUE(execution_id, sequence)`, `UNIQUE(tool_execution_uid)`. Inserts use insert-or-ignore semantics
(catch `DataIntegrityViolationException` → treat as already-recorded, no duplicate, no error). Ids are
stable (the run's UUID + monotonic sequence + per-tool UUID) — never random-per-attempt.

## 11. Ownership & access
Every read is `owner_id`-scoped **in SQL** (never load-all-then-filter); a non-owner or missing id →
**404** (existence-masking, matching M3/M5/M7). `conversation_id` is a filter, **never** an
authorization claim. USER and ADMIN follow the same owner scope in M9 (no cross-user path). Identity
always from `@AuthenticationPrincipal`.

## 12. API (read-only; `/api/v1/agent`)
- `GET /api/v1/agent/executions` — owner's executions, **paginated** (`page`, `size`, `sort`), filters:
  `status`, `conversationId`, `from`/`to` (date range), `toolName` (optional). Bounded page size.
  Returns `PageResponse<AgentExecutionSummary>` (executionId, status, conversationId, startedAt,
  completedAt, durationMs, iterations, toolCalls, failureCode).
- `GET /api/v1/agent/executions/{executionId}` — owner's execution detail: the summary plus ordered
  `steps` (sequence, type, status, toolName, detailCode, durationMs) and `toolExecutions` (toolName,
  riskLevel, outcome, errorCode, confirmationId, durationMs) and the bounded `finalResponseSummary`.
  Non-owner/missing → 404. No new write endpoints — audit is append-only via the internal listener.

Sanitization: responses expose **no** internal Java class names, stack traces, raw prompts, raw
arguments, raw LLM output, chain-of-thought, JWTs, secrets, hidden system prompts, or confirmation
secrets — only the safe columns above. All via response records; entities never cross the boundary.

## 13. Retention
Documented policy, **no scheduler in M9**: `AGENT_AUDIT_RETENTION_DAYS` (default 90) is defined and
documented as the intended retention horizon; automated purge is deferred to a future maintenance
milestone (M10+). Distinct from M7 memory TTL: **memory is short-lived (Redis TTL); audit is durable
with a defined retention** — the two never share semantics or storage.

## 14. Observability (M9-internal only; M10 owns dashboards)
Micrometer counters: `audit.execution.created`, `audit.step.created`, `audit.tool_execution.created`,
`audit.write.success`, `audit.write.failure` (low-cardinality: `stepType`/`outcome` where useful, never
userId/conversationId/args). Does **not** duplicate M8 `guardrail.*` metrics. Structured logs carry
`executionId`/`stepSequence`; never raw content.

## 15. Performance
Audit adds N short inserts per run (~1 execution + ~1 step/iteration + 1 per tool + 1 completion). Each
is a small indexed insert outside any LLM/tool transaction; best-effort so it never blocks. `duration_ms`
is measured, never fabricated. Token usage is **not** stored (M4 avoided fabricating counts; M9 does not
invent them). Real audit-write timing to be **measured** (Testcontainers) before any performance claim.

## 16. Testing
- **Unit (`AuditService`, mapped repos):** status transitions; idempotent double-insert; payload
  redaction (no raw content persisted); ownership scoping; best-effort swallow of a write failure
  (+metric); `NoOpAgentExecutionListener` truly no-ops.
- **Repository (Testcontainers Postgres):** persistence, `UNIQUE(execution_uid)` /
  `UNIQUE(execution_id, sequence)` / `UNIQUE(tool_execution_uid)` constraints, owner-scoped + paginated
  queries, index-backed sort.
- **Integration (real Postgres+Redis):** create execution → steps → tool execution → complete/fail;
  query by owner/conversation; pagination; duplicate-prevention.
- **End-to-end:** real agent → guardrail → tool → audit → PostgreSQL; assert the execution + steps +
  tool_execution exist and are accurate; the M8 confirm flow appends `CONFIRMATION_APPROVED` +
  `tool_execution` and promotes the execution to `COMPLETED`.
- **Security:** User A cannot read User B's execution (404); a conversationId filter cannot cross
  ownership; API returns no raw prompt/args/LLM-output/chain-of-thought/secrets/stack trace/confirmation
  secret; admin has no cross-user path in M9. Coverage gate ≥0.75 held; live-Ollama tests stay gated.

## 17. Failure model (surfaced codes)
Read API: `404 EXECUTION_NOT_FOUND` (masked), `400 VALIDATION_ERROR` (bad filter/paging), `401`/`403`
via the standard `ApiError`. Internal audit-write failure is **not** an API error — it is a WARN +
`audit.write.failure` metric.

## 18. M10 boundary
M9 emits audit rows + minimal internal metrics. Dashboards, aggregation, alerting, cross-user analytics,
and any purge scheduler are **M10+ (PLANNED)**.

## 19. ADRs
- **ADR-0026** Durable Agent Audit Model (three typed tables, no generic events table, UUID natural
  keys, listener seam).
- **ADR-0027** Audit Transaction & Failure Semantics (best-effort, REQUIRES_NEW, never on the decision
